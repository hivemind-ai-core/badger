How to read these results


Bars and points show medians of independent fresh-process trial medians, with min/max whiskers across those trials. CV above 10% is flagged. Warm iterations in a process share JIT, heap, caches, and worker pools; they are correlated. All allocations and normal GC remain enabled. There is no combined winner score.


Badger uses optimized source JIT; Go uses a native release binary; Node uses its normal V8 JIT; Java runs javac classes on HotSpot with its default tiered JIT and GC. READY is observed by the parent after module loading and Badger’s front-end/JIT compilation, before fixture loading or worker-pool creation. A common tiny native measurement launcher adds one fork/exec to startup and whole-process wall time. It is not a cold-disk or deployment-readiness measure. Whole-process time includes all warmups, samples, fixture reads, printing, pool teardown, and shutdown.


Preparation means Badger source → saved MIR (front end only), Go’s cached go build, Java javac --release 21 classes, and N/A for Node. Saved MIR is not the measured Badger mode. Badger launch compilation is the CLI’s full compilation duration rounded to 0.001 ms; it is contained in startup. Go build, Badger compile and javac produce different products; javac bytecode still needs JVM loading and JIT. Java class loading and tiered compilation continue into first/warm execution. The short default warmup does not prove JVM steady state. Node parsing and incremental V8 JIT remain in startup/first/warm execution; no fictitious separate compile time is assigned.


Peak RSS comes from Linux wait4 in a clean native launcher, avoiding an inherited parent-memory floor. It includes the entire process, JIT, input fixture, and all threads, and is the high-water mark across warmups and samples. It is not live heap size, per-operation allocation, or steady-state service memory.


Messaging and pipeline move materialized 64-ID batches through one producer, bounded input capacity 4, N consumers, and a reduction. Badger and Go have bounded result channels of 4. Java uses standard ArrayBlockingQueue input/results (capacity 4), N consumer tasks plus a producer on a persistent fixed thread pool, and poison-pill shutdown. Java pool creation is in the first iteration and shutdown is in whole-process time. Its producer and main coordinator are additional platform threads; JVM compiler/GC threads use default ergonomics. Node uses a main-thread dispatcher, four queued batches and one in flight per worker; result events are reduced immediately. Node structured-clones batches, while Go and Badger pass references. Node thread creation occurs in the first execution and warm iterations reuse the pool. Go/Badger tasks are recreated per iteration on their persistent runtime worker threads. Node has N worker threads plus a coordinating main thread; worker count is not a strict total CPU cap. These are application implementations, not identical queue kernels.


The JSON fixture contains escaped quotes and UTF-8 text. Every port parses an order, enriches it, serializes it and reparses the result. JSON libraries and validation are language-native and have different guarantees on invalid data; only valid shared input is measured. Java uses pinned Gson 2.14.0; the jar and JDK runtime/library hashes are retained in the evidence. Reconciliation materializes input/enriched rows, joins discounts and groups by customer. State retains immutable snapshots; mutable-map ports copy only when retaining a version.


These bounded batch jobs model service components and integration work. They do not measure HTTP, databases, network latency, durable side effects, sustained service latency, or failure recovery. Short runs, host load, CPU quotas and power policy can affect results. Compare within a cohort and inspect raw ranges before claiming a regression.
